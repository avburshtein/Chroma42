# Роадмап Chroma42

**Версия:** 2.0.0 · **Статус:** рабочий план проекта

Объединяет движки, методологию, экспорт, интеграции и документацию.
Нормативные требования — в [методологии](../Chroma42%20Color%20Pair%20Methodology.md),
устройство — в [архитектуре](../Общая%20архитектура%20Chroma42.md).

---

## 0. Как читать роадмап

Каждый этап имеет три оценки:

| Оценка | Значение |
|---|---|
| **Ценность** | Что даёт пользователю: `низкая` / `средняя` / `высокая` |
| **Трудозатраты** | `S` (дни) / `M` (недели) / `L` (месяцы) |
| **Приоритет** | `MVP` / `1.0` / `2.0` — в каком релизе обязательно |

Приоритет означает: этап без этого релиза **не выпускается**. Этапы
с низким приоритетом можно отложить без потери ценности продукта.

## Этап 6. Раскладка семантических токенов по режимам

**Ценность:** высокая · **Трудозатраты:** M · **Приоритет:** MVP

Сейчас раскладка `modes` существует как модель типа, но не заполнена
движком: тесты собирают токены вручную.

Что сделать:

1. Реализовать генерацию `Modes` для всех 6 режимов из примитивов.
2. Применить солвер: для каждого режима подобрать тона, проходящие порог
   политики.
3. Задать базовые привязки: `surface` = `neutral.99` в light,
   `neutral.5` в dark.
4. Обработать случаи, где солвер не достигает порога: пометить токен
   и выдать предупреждение с рекомендацией сменить сид.

Результат: тема собирается одной функцией из 8 сидов.

## Этап 7. Экспорт в CSS Variables

**Ценность:** высокая · **Трудозатраты:** S · **Приоритет:** MVP

Структура вывода:

```css
:root                                  /* базовые значения */
[data-theme="light"]                   /* схема */
[data-theme="light"][data-contrast="normal"]
[data-theme="light"][data-contrast="medium"]
[data-theme="light"][data-contrast="high"]
[data-theme="dark"]                    /* и зеркально для dark */
```

Дополнительно:

- альфа-цвета и их непрозрачные фолбэки;
- блок `@media (prefers-reduced-transparency: reduce)`;
- токены эффектов: blur, shadow, scrim;
- кнопка «Скопировать CSS».

## Этап 8. Экспорт в Tailwind v3 и v4

**Ценность:** высокая · **Трудозатраты:** S · **Приоритет:** MVP

Tailwind v3 — конфиг с `rgb(var(--chroma-*-rgb) / <alpha-value>)`.

Tailwind v4 — блок `@theme`, связывающий токены с CSS-переменными.

Переключатель версии в интерфейсе, инструкция по подключению
в комплекте с экспортом.

## Этап 10. Превью компонентов

**Ценность:** средняя · **Трудозатраты:** M · **Приоритет:** 1.0

Показать тему в реальном интерфейсе, а не квадратиками.

Компоненты: кнопка, инпут, карточка, бейдж, алерт, навигация, таблица,
переключатель, чекбокс, тост, ошибка формы, фокус-состояние,
disabled-состояние. Используются только семантические токены.

Переключение режимов прямо в превью; контраст показывается на самом
компоненте.

> Токены и компоненты, удалённые при чистке проекта, восстанавливаются
> из коммита `375b3a5` — именно для этого этапа.

## Этап 11. Шаринг темы по URL

**Ценность:** средняя · **Трудозатраты:** S · **Приоритет:** 1.0

1. Сериализация: `{ version, engine, policy, seeds }`.
2. Сжатие через `lz-string`.
3. Формат ссылки: `#s=...`.
4. Обработка повреждённых и устаревших ссылок: версия проверяется,
   неизвестная отклоняется с понятным сообщением.

В ссылку кладются **только сиды**, а не готовая тема: получатель
пересчитывает шкалы своим движком. Это сжимает ссылку в разы и гарантирует
одинаковый результат при любой версии движка.

## Этап 12. Импорт существующих токенов

**Ценность:** средняя · **Трудозатраты:** M · **Приоритет:** 1.0

Порядок поддержки: Chroma42 JSON → DTCG-подобный JSON → CSS variables.

неизвестных версий, отчёт «что импортировано / что не распознано».

## Этап 17. Figma

**Ценность:** средняя · **Трудозатраты:** L / S · **Приоритет:** 2.0

Разделено на две части с очень разной ценностью:

- **S, высокая ценность:** экспорт JSON, пригодный для плагинов
  «JSON to Variables» и подобных. Работает с любым сторонним плагином.
- **L, спорная ценность:** собственный плагин Chroma42. Месяцы работы
  ради одного канала распространения, тогда как Figma Variables можно
  заполнить из JSON сторонним инструментом.

Рекомендация: делать S-часть. L-часть — только при наличии спроса.

## 3. Порядок работ

Критический путь к MVP:

```text
Этап 6  (раскладка по режимам)   <- блокирует всё остальное
   │
   ├──> Этап 7  (CSS)      ──┐
   ├──> Этап 8  (Tailwind) ──┼──> Этап 9 (аудит-панель) ──> MVP
   └──> Этап 11 (URL)      ──┘
```

Этап 6 обязателен первым: без заполненных `modes` ни экспорт, ни аудит
не имеют смысла. Этапы 7 и 8 независимы и выполняются параллельно.

## 4. Технические долги

| Долг | Влияние | Оценка |
|---|---|---|
| Порог 4.5:1 для нетекстовых контекстов зашит как `NON_TEXT_CONTEXTS` | При изменении WCAG потребуется ревизия; сейчас это политика проекта, а не норма | S |
| Пара `focus-ring/surface` — упрощение относительно SC 2.4.13 | Не покрывает требование «кольцо против нефокусированного состояния» | M |
| Ширина реестра ограничена 30 парами | Специфические пары продукта добавляются пользователем вручную | S |
| Раскладка режимов собирается вручную в тестах | Дублирование логики; исчезнет после этапа 6 | S |

## Этап 15. Симуляции цветовой слепоты

**Ценность:** низкая · **Трудозатраты:** M · **Приоритет:** 2.0

Протанопия, дейтеранопия, тританопия, grayscale. Проверка пар
`success/error`, `success/warning`, `info/primary`.

**Обязательное ограничение в интерфейсе:** симуляции — эвристика без
нормативных порогов. Результат — рекомендация добавить нецветовой признак,
а не блокировка экспорта.
